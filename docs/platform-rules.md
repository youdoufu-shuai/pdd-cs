# 拼多多客服平台规则清单与工程落地

> 版本：2026-10（对应代码 v1.0.0）
> 适用：拼多多店铺在线客服（多多客服）自动接待
> 结论口径：**平台规则以商家后台「规则中心」当日生效版本为准**。官方规则中心需要商家登录，
> 本文件把能查到的依据分级标注，作为本项目的工程实现依据，不构成法律意见。

## 证据等级说明

| 等级 | 含义 | 本项目中的用法 |
| --- | --- | --- |
| **A** | 法律法规原文 / 国家标准发布信息 / 权威媒体报道 | 作为硬约束写入合规层与产品设计 |
| **B** | 商家后台页面原文 / 一线实测 / 可复现操作经验 | 作为词表、判罚口径、话术红线的依据 |
| **C** | 公开二手信息 / 行业文章 / 项目文档说明 | 作为默认值参考，上线前需后台核对 |

平台规则随时可能调整。**本项目不把任何考核数值写死在代码里**，全部落在
`config/config.yaml` 与 `config/rules/*.yaml`，便于按后台当日口径调整。

## 一、客服响应与考核

### 1.1 回复率指标（证据等级 C，待后台核对）

公开资料中对拼多多客服回复率的描述为：

> 拼多多客服回复率分为 5 分钟、15 分钟、1 小时回复率，回复率高低影响店铺能否参加平台活动；
> 5 分钟回复率指最近 3 天在 5 分钟内回复的指标。

另有电商从业者提到「3 分钟人工回复率」考核口径。两者都可能随平台规则调整，
且不同店铺/类目/活动期的口径可能不同。

**工程落地**

- `compliance.sla.first_response_seconds`（默认 180 秒）：首响红线，可在面板查看达标率；
- `compliance.sla.warn_seconds`（默认 120 秒）：未回复会话告警阈值；
- 面板展示：会话数、自动回复数、平均首响、P90 首响、达标率、超时等待会话；
- 首响从「客户最后一条未被回复的消息」开始计时，自动回复发出即结束计时。

**为什么这样落地**：即使平台考核口径变化，「尽量快、别漏回、超时告警」都是正确方向；
具体达标线由运营在配置里按后台规则调整，不写死。

### 1.2 回复内容不得重复（证据等级 B）

ChatGPT-On-CS 项目在关键词回复说明中明确提到：

> 在拼多多平台等平台，是不允许每次重复一个回答的，所以可以插入一个随机符，以规避这个问题。

并在实现中用 `[~]` 占位符随机插入字符/表情。

**工程落地**

- `compliance.anti_duplicate`：对同一会话最近 N 条回复做字符二元组相似度检测；
- 相似度 ≥ `min_unique_ratio`（默认 0.86）视为重复，自动多样化：
  `[or]` 候选轮换 → `[~]` 随机符 → 语气/句式变体（长后缀降低相似度）；
- 风控日志记录重复检测情况，便于复盘。

### 1.3 敏感词与拦截（证据等级 B）

金销智服《拼多多和抖店的客服有什么不一样？换平台最容易踩的几处》（2026-08-25，一线操作经验）提到：

> 实际发送时遇到过，比如在拼多多，"链接""专业人员"这类词会被拦截，同样的说法换一种表达方式就没事。

同一篇文章强调：这不是平台公开的违禁词清单，平台判定逻辑会调整，不能死记穷举。

**工程落地**

- `config/rules/compliance.yaml` 的 `sensitive` 词表内置这两个实测词；
- `rewrite_map` 自动替换：「链接」→「页面」、「专业人员」→「售后同事」；
- 引擎在发送前检查、替换、二次检查，无法消除则改用兜底话术并转人工；
- 风控日志记录 `content_rewritten` / `content_blocked` 事件。

**上线前建议**：用测试客户把高频话术各发一遍，观察是否被拦截（平台拦截通常表现为发送失败或消息不显示），
把新增敏感词补进 `compliance.yaml`。

### 1.4 负体验扣款（证据等级 B，直接资金风险）

金销智服《拼多多负体验是什么？处罚单上常见的这几类情形》（2026-08-26）从商家后台
处罚详情页抄录了以下判罚口径原文（样本为 2026 年 8 月、百单级，非平台公开分类表）：

1. **商品未达预期**
   > 结合消费者反馈，商品存在未达预期的问题（如少发、描述不符、质量问题、发错货或磨损等）
2. **发货物流信息不实**
   > 消费者咨询发货、物流问题时，商家提供不符合实际情况的信息
3. **消费者体验受损**
   > 因消费者体验受损将扣款 3 元补偿消费者（金额随单不同，不是固定值）

其中第 2 类**证据在聊天记录里**：客服说过的「今天一定发」「明天到」「已经在路上了」，
一旦与实际物流状态对不上，就可能落入此类判罚。

**工程落地**

- `promises` 拦截（`config/rules/compliance.yaml`）覆盖四类：
  - 发货时效承诺：今天发 / 明天发 / 马上发 / 一定发 / 保证发……
  - 物流到达承诺：明天到 / 一定到 / 次日达 / 三天内到……
  - 售后承诺：包退 / 包换 / 肯定能退 / 我帮你申请仅退款 / 我说了算……
  - 赔付承诺：赔你 / 补偿你 / 三倍赔偿 / 假一赔十……
- 命中后：改写为兜底话术（“具体时效和售后处理以商品详情页与平台页面为准，我帮您转人工确认”）+ 转人工 + 风控日志；
- AI 提示词（`engine/ai.py::HARD_RULES`）把同样的约束写给模型；
- 关键词话术库（`keywords.yaml`）本身也按此口径编写，发货/物流/售后统一回答“以详情页/平台页面为准”。

### 1.5 规则公示与版本（证据等级 A）

《网络交易平台规则监督管理办法》自 **2026-02-01** 起施行。金销智服《处罚依据的规则版本怎么查？
后台这三个位置要一起截》引述该办法：

- 平台修改规则应当至少提前 **7 日** 公示；涉及用户数量巨大、修改内容较多或经营者消费者
  重要权益的，至少提前 **15 日**；
- 应完整保存修改后版本生效前 **3 年** 的全部历史版本，供经营者和消费者查阅、下载。

**工程落地**

- 对话与回复、风控事件全部落 SQLite 并带北京时间戳；
- `python -m pdd_cs export` 导出 JSON，用于申诉取证的素材整理；
- 本文件的每条规则标注来源与日期，平台变更时按流程更新。

### 1.6 人机协同客服国家标准 GB/T 47746—2026（证据等级 A）

- **名称**：《顾客联络服务 人工与智能客户服务协同要求》
- **发布**：市场监管总局、国家标准化管理委员会
- **实施**：2026-09-01
- **性质**：推荐性国家标准（GB/T），**不是强制规定、不设罚则、没有认证机制**；
  起草单位 32 家，其中没有电商平台；目前没有公开信息显示拼多多等平台据此调整商家考核规则。

公开报道中可确认的具体要求（三条）：

1. 简单标准化问题由智能客服快速响应；
2. 复杂个性化需求及涉及人身财产安全的场景**优先接入人工**（原文是“优先”不是“必须”）；
3. 人机切换要同步传递客户身份信息与历史交互记录，**不应要求客户重复陈述**。

另有总体要求涉及客服入口位置等（针对企业自建网站，电商店铺入口由平台定义，商家改不了）。

**工程落地（按标准方向做产品设计，不宣称“符合国标”）**

- 首条自动回复披露智能客服身份并告知如何转人工（`compliance.disclosure`）；
- 转人工信号覆盖：人身安全、监管/法律、明确要求人工、投诉、售后、价格谈判、大额订单、
  情绪激动、重复追问、关键词（`engine/compliance.py::handoff_signal`，优先级从高到低）；
- 转人工前发送提示，并在面板/数据库中保留完整对话，人工接手即可看到上下文；
- 系统不做“通过国标”之类的对外宣传。

### 1.7 平台规则告知与扣款计算（证据等级 A）

《网络交易平台规则监督管理办法》中与商家权益直接相关的条款（金销智服系列文章引述）：

| 条款 | 要点 | 对客服的含义 |
| --- | --- | --- |
| 第 19 条 | 平台采取对商家权益有负面影响的措施时，应告知事实、理由、依据 | 扣款/处罚先看后台处罚详情，保留证据 |
| 第 27 条 | 仅退款相关规则（“仅退款全面取消”系误读） | 客服不得答“可以仅退款/我说了算”，一律“以平台页面为准” |
| 第 29 条 | 平台应说明扣款金额计算方式 | 金额对不上时按导出记录核对 |

**工程落地**：客服知识库 `pdd-rules.md` 固定口径；承诺/规则冒充拦截；导出功能支持复盘。

## 二、拼多多客服操作口径（证据等级 C，来自项目文档与行业实践）

以下内容来自 ChatGPT-On-CS、pdd-auto-reply 等开源项目的实现经验，以及金销智服公开文章，
属于操作层面事实/经验，平台改版后可能变化：

| 事项 | 口径 | 代码/配置落点 |
| --- | --- | --- |
| 客服工作台 | 多多客服是独立应用，与千牛/飞鸽不同；子账号独立开通 | 单店铺单账号设计 |
| 消息类型 | 文本、图片、视频、表情、撤回、商品咨询、商品规格、订单、转接 | `pdd/message.py` |
| 是否发货 | 平台判断“是否发货”看系统里有没有运单号，不看仓库动作 | 知识库 `pdd-rules.md` |
| 改地址 | 发货前引导客户在订单页自行修改；已发货需人工联系快递 | 转人工关键词 + 知识库 |
| 拦截包裹 | 平台不收费，但快递公司可能收费 | 知识库（转人工处理） |
| 尺码 | 告知参数可自动答；推荐码数（卡在两个码之间）需转人工 | `keywords.yaml` + 知识库 |
| 生产日期/库存 | 随批次变化，不写死；答“怎么查/以实物为准” | 知识库 `product-faq.md` |
| 运费险 | 只答“本店本商品有没有”，理赔与赔付交平台/保险 | 知识库 `store-policy.md` |
| 发货时效 | 自动回复口径必须与商品详情页公示完全一致 | 知识库 + 承诺拦截 |
| 发票 | 开票信息需人工核对 | 转人工关键词 |
| 售后 | 售后按平台页面流程处理，客服不承诺结果 | 转人工 + 承诺拦截 |

## 四、上线前必须在商家后台核对的事项

1. **客服考核**：规则中心/search「客服」相关规则，确认当前回复率的统计口径、达标线、考核时段。
2. **智能客服/自动回复**：确认平台是否要求报备、是否允许第三方工具接入（以合作协议与规则中心为准）。
3. **敏感词**：用测试账号把 `keywords.yaml` 全部话术试发一遍，把被拦截词补进 `compliance.yaml`。
4. **负体验**：打开一张处罚详情页，核对凭证要求、申诉窗口、金额计算方式。
5. **售后/仅退款**：核对店铺当前售后政策与平台最新细则，更新 `knowledge/store-policy.md`。
6. **大促规则**：大促期发货时效、售后时效可能有特殊规则，提前调整知识库与话术。

## 五、规则更新流程

```
平台规则变化
   ↓
更新 docs/platform-rules.md（来源/日期/证据等级）
   ↓
改 config/rules/*.yaml 或 config/config.yaml（不写死代码）
   ↓
python -m pdd_cs simulate "触发场景"   # 决策回归
python -m pytest -q                    # 自动化测试
   ↓
小流量灰度 → 面板看风控日志 → 全量
```

## 五（补充）、规则风险的日常巡检与告警

平台规则的风险不止“发送那一刻”，日常运营还需要三件事：

1. **上线前体检（lint）**：`python -m pdd_cs lint --strict` 扫描关键词话术、商品回复、
   知识库、人设里的承诺/导流/敏感词/绝对化用语，把风险挡在发送之前；
2. **事后抽检（qc）**：`python -m pdd_cs qc --days 7` 按规则找出乱承诺、漏回、首响超时、
   重复话术、投诉信号、转人工失败等会话，供主管复盘与培训（对应 GB/T 47746 人机协同中
   “复杂问题该转人工有没有转”的自查方向）；
3. **异常告警（alerts）**：登录态过期、长连接断开、转人工失败、客户超时未回，
   实时推送到钉钉/飞书/企业微信群——这类问题不解决，比“答错一句”更容易造成投诉与考核扣分。

这些能力都不改变实时拦截逻辑：发送前的合规检查仍然强制生效，巡检与告警是第二道防线。
